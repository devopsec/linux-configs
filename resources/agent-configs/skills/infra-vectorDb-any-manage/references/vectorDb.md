## Select a store

| Store | Prefer when | Main tradeoff |
|---|---|---|
| PostgreSQL + pgvector | Existing PostgreSQL, transactional joins/RLS, moderate corpus and operational familiarity. | Filtered ANN recall and index memory/build time. |
| Qdrant | Heavy filtered ANN, payload indexes, dense+sparse/hybrid retrieval, larger vector workloads. | Separate service to secure, operate, and back up. |
| Weaviate | Schema-first/vector-native operations fit the application. | Module/vectorizer and service-version coupling; review outbound API calls. |

Use Cloud SQL/managed service compatibility matrices for extension availability; an upstream extension version is not proof that a managed database offers it.

## pgvector

```sql
CREATE EXTENSION IF NOT EXISTS vector;
SELECT extversion FROM pg_extension WHERE extname = 'vector';
CREATE TABLE chunks (
    id text PRIMARY KEY,
    tenant_id text NOT NULL,
    acl text[] NOT NULL DEFAULT '{}',
    doc_id text NOT NULL,
    content text NOT NULL,
    content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    embedding_model text NOT NULL,
    embedding vector(1024) NOT NULL
);
CREATE INDEX chunks_tenant_idx ON chunks (tenant_id);
CREATE INDEX chunks_content_tsv_idx ON chunks USING gin (content_tsv);
CREATE INDEX chunks_embedding_hnsw ON chunks
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

Choose dimensions and operator class to match the embedding model and distance metric. HNSW usually favors recall/latency but costs memory/build time; IVFFlat is useful when data is loaded before index creation and a smaller index is preferred.

```sql
BEGIN;
SET LOCAL hnsw.ef_search = 100;
SET LOCAL hnsw.iterative_scan = relaxed_order;
SELECT id, content
FROM chunks
WHERE tenant_id = $1 AND acl && $3::text[]
ORDER BY embedding <=> $2::vector
LIMIT 10;
COMMIT;
```

Enable RLS and set tenant context transaction-locally; the application role must not own the table or have `BYPASSRLS`. Use `EXPLAIN (ANALYZE, BUFFERS)` and compare ANN results with exact results on representative selective filters. `VACUUM (ANALYZE)` after churn; `REINDEX ... CONCURRENTLY` is an approved production change, not an automatic response.

```sql
ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY chunks_tenant_isolation ON chunks
  USING (tenant_id = current_setting('app.tenant_id', true))
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true));
BEGIN;
SELECT set_config('app.tenant_id', $1, true);
-- run parameterized queries inside the same transaction
COMMIT;
```

## Qdrant

Run a pinned, private image; require API key/TLS and persistent storage. Attach it to a pre-created internal Docker network named `private-ai-net` with no host ports published; use an approved authenticated proxy for clients:

```bash
docker run --name qdrant \
    --network private-ai-net \
    --env QDRANT__SERVICE__API_KEY="${QDRANT_API_KEY:?inject from Secret Manager}" \
    --env QDRANT__SERVICE__READ_ONLY_API_KEY="${QDRANT_RO_API_KEY:?inject from Secret Manager}" \
    --env QDRANT__TELEMETRY_DISABLED=true \
    --volume qdrant-storage:/qdrant/storage \
    docker.io/qdrant/qdrant:v1.20.0
```

Configure collection dimensions/distance, payload indexes for tenant/ACL filters, and an appropriate replication factor for distributed availability. Use on-disk vectors/quantization only after recall tests; filter every query by authenticated tenant identity.

Take a fresh snapshot before collection replacement or restore. Confirm target, snapshot name, and recovery impact; restore can replace live data. Store snapshot copies in an approved private backup bucket and test restore/count/recall in an isolated environment.

For an API snapshot, authenticate every call with the Qdrant API key; creation/list/download use the collection's `/snapshots` endpoints:

```bash
curl \
    --fail --silent --show-error \
    --header "api-key: ${QDRANT_API_KEY:?inject from Secret Manager}" \
    --request POST "${QDRANT_URL}/collections/${COLLECTION}/snapshots"
```

Recovery uses `PUT /collections/<collection>/snapshots/recover`. Confirm snapshot and target before recovery.

## Weaviate

Pin the image to `cr.weaviate.io/semitechnologies/weaviate:v1.40.2`; disable anonymous access, enable API-key authentication/authorization, use persistent storage, and publish no host ports. Use `DEFAULT_VECTORIZER_MODULE: none` when vectors are generated by the application; enable a module only after reviewing its external data flow.

```yaml
services:
  weaviate:
    image: cr.weaviate.io/semitechnologies/weaviate:v1.40.2
    environment:
      AUTHENTICATION_ANONYMOUS_ACCESS_ENABLED: "false"
      AUTHENTICATION_APIKEY_ENABLED: "true"
      AUTHENTICATION_APIKEY_ALLOWED_KEYS: "${WEAVIATE_API_KEY:?inject from Secret Manager}"
      AUTHENTICATION_APIKEY_USERS: "admin"
      AUTHORIZATION_ADMINLIST_ENABLED: "true"
      AUTHORIZATION_ADMINLIST_USERS: "admin"
      PERSISTENCE_DATA_PATH: /var/lib/weaviate
      DEFAULT_VECTORIZER_MODULE: none
    volumes: [weaviate-data:/var/lib/weaviate]
    networks: [private-ai-net]
volumes: {weaviate-data: {}}
networks:
  private-ai-net:
    external: true
```

## Backups and verification

- PostgreSQL: managed backups/PITR or encrypted `pg_dump`/physical backups; restore into a clone before relying on a recovery plan.
- Qdrant/Weaviate: take native snapshots/backup artifacts and test recovery with the same compatible version.
- Keep source snapshots and deterministic embedding pipelines so vectors can be rebuilt; that is a secondary recovery path, not a substitute for backups.
- Before a destructive change, verify the database/collection name, tenant boundary, backup freshness, RPO/RTO, and approval. After recovery, verify object counts, schema/index state, tenant filtering, and sampled recall.
